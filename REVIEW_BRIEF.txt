REVIEW REQUEST v2 — staledep: stale-dependency detection in LLM agent trajectories

This supersedes an earlier brief. Two reviews of that version established that
its headline results were artifacts. Those are retracted below, and the design
changed in response. Attack this version as hard as you attacked the last one.

--------------------------------------------------------------------------------
0. WHAT CHANGED SINCE v1 (retractions, unprompted)

RETRACTED - "capability correlates with exposure". Artifact. Binary
per-trajectory candidate rate tracked how many calls a model made before
stopping. Normalising by tool call scrambles the ranking: a configuration near
the bottom of the binary table (claude-3-sonnet-repeat_user_prompt, 38.7%) has
the HIGHEST candidate density per call (0.398).

RETRACTED - "prompt-injection defenses don't help". Definitionally expected.
Those defenses operate on message content and cannot change the read/act
structure of a benign trajectory. tool_filter, the only one that moves the
number, does so by removing authority, which is least privilege, not a fake
defense.

RETRACTED - "3.5x higher than the published 12%". Numerology. It multiplied
incompatible experimental units.

RENAMED - findings are "stale-dependency candidates", not vulnerabilities.
Read-then-act is the definition of agency. Copying a checked value into an
action often PREVENTS retargeting rather than enabling it: read_file ->
send_money(literal_amount) is a snapshot, not a race.

RENAMED - "argument provenance" is now "lexical lineage". String and token
overlap is evidence, not causality.

RENAMED - project was AgentTX, which collides with an existing npm package.

--------------------------------------------------------------------------------
1. WHAT IT IS NOW

A measurement instrument, explicitly not a scanner. It finds places where an
agent reads state and later acts on it, and reports how many of those an
adversary is actually in a position to move.

A defensible vulnerability claim needs four conditions. This establishes part of
the first, and the mutation harness is a first attempt at the second and fourth:

  1. the action causally depends on the earlier observation
  2. a stated attacker can mutate the relevant state during the interval
  3. that mutation invalidates a predicate or rebinds the action
  4. the unsafe action still commits

--------------------------------------------------------------------------------
2. RESULTS

Over 2,540 attack-free trajectories from 29 model/configuration pairs (NOT 29
independent models) shipped with AgentDojo.

Conditioned on who can move the resource:

  suite       candidate   strict   moderate   multi-agent
  banking        47.8%     11.3%      34.3%        47.1%
  slack          73.4%     48.2%      48.2%        73.4%
  travel         26.2%      0.0%      26.2%        26.2%
  workspace      39.8%     39.8%      39.8%        39.8%
  overall        45.4%     28.7%      37.9%        45.3%
  high-risk               10.6%      15.2%        15.7%

strict = arbitrary third parties only. moderate adds counterparties writing
their own records. multi_agent adds concurrent agents and is near-unconditioned.

Travel collapses to 0.0% under strict: every travel candidate is a provider
changing its own prices, which is a business race, not a security one. That the
filter annihilates a whole suite is the check that it is not vacuous. A first
pass folded concurrent agents into the attacker set and removed 0.1% of
candidates -- vacuous -- which is the same too-liberal failure as the original
metric.

RECALL, by seeded dependency class (12 synthetic trajectories):
  flagged by any rule                6/12  (50%)
  handled by the intended mechanism  3/12  (25%)

Three catches are incidental: a control dependence is caught only because the
sink declares the same resource, an alias never has to be resolved when both
calls touch one coarse resource, and a phantom is caught on a literal amount.

NO coverage at all: negative evidence, aggregates, derived values (currency
conversion), laundering through an intermediate tool, implicit reads inside
write tools, cross-system policy dependence. Aggregates and derived values are
exactly what invoice work produces.

ATTACK RUNS contain no free exploitability evidence. Over 30,366 attack-active
trajectories:

                                   attack-active   attack-free
  mean tool calls                       4.1            3.8
  read -> mutate -> use on one resource 4.90%          3.23%
    of which agent self-batching        3.85%          2.52%
    cross-tool mutation                 1.05%          0.71%

Dominated by the agent batching its own writes. AgentDojo's injections redirect
the agent's goal; they do not move state it already checked.

--------------------------------------------------------------------------------
3. A MEASUREMENT THAT WAS WRONG, AND WHY (worth attacking further)

The first attempt at the above returned exactly 0.00%, cleanly and plausibly.
It was an artifact of my own code: find_windows() invalidates a check when
something writes the checked resource, so "a window containing a mutation of its
own resource" is definitionally empty. I nearly published a confident false
negative with a mechanical cause three lines deep in my own detector.

Candidate detection and exploitation detection need different logic. This is the
third time in this project a number looked right and was not, which is the main
reason I now regard the seeded-recall harness and the mutation controls as the
actual contribution rather than any figure.

--------------------------------------------------------------------------------
4. THE MUTATION HARNESS (new, results pending)

AgentDojo has no primitive for moving state between tool calls, so one was
built. Two guards against the obvious criticisms:

Against circularity: mutation targets are declared per suite UP FRONT, keyed to
the resource they move and the attacker tier required, and the sweep fires
blindly at every inter-call gap. The detector does not choose where to strike.

Against measuring corruption instead of timing: a hit counts only when an
interior gap changes the outcome while BOTH controls -- before the first call,
after the last -- leave it unchanged. A mutation that changes things from any
position is simply breaking state.

One mutation (swap_iban) is included that SHOULD NOT COUNT: it is declared
writable only by the principal. A TOCTOU verdict on it would mean the harness is
measuring corruption and the setup is wrong.

--------------------------------------------------------------------------------
5. KNOWN LIMITATIONS

- Not prevalence. Precision-adjusting a flagged rate does not give prevalence
  while false negatives are unquantified.
- Precision ~93% from three hand-audited samples of 14-18. Interval roughly
  70-99%. Too small to stratify by suite, signal, or risk tier.
- Effect declarations are self-reported. A tool that under-declares silently
  removes edges. This trust assumption does structural work.
- Resource granularity is coarse. Versioning a whole record aborts on an
  irrelevant field change -- an availability attack, and a false-abort source.
- 2,756 attack-free files exist; 216 zero-call trajectories excluded; 57
  upstream model-task cells absent.
- Benign false-abort rate is NOT measured. This is the metric that decides
  whether any enforcement built on this is deployable, and it does not exist yet.

6. WHAT I WANT FROM YOU

  a. Is the strict-threat-model number (28.7%, 10.6% at high-risk sinks) a
     threat statement, or still substantially tautological?

  b. The mutability annotations are judgements about AgentDojo environments, not
     facts. Which assignments would you contest? Is "calendar is untrusted
     because external invitees write it" defensible?

  c. Attack the mutation harness controls. Is "interior gap changes the outcome,
     both controls do not" sufficient to distinguish TOCTOU from corruption?
     What confound survives it?

  d. Given 25% mechanism coverage on seeded classes, is this instrument worth
     publishing as-is, or does the aggregate/derived-value gap disqualify it for
     financial workloads specifically?

  e. Enforcement is not built. The plan was version-pinned capability tokens;
     review established that (i) middleware validate-then-forward has its own
     check-use gap, and (ii) pre-check poisoning -- where state is already
     hostile when first read -- is untouched by version pinning and is probably
     the larger real attack surface. Is there a version of enforcement worth
     building at the middleware layer at all, or is the honest conclusion that
     this must be done at the resource?

  f. What is the smallest experiment that would falsify the whole premise?
